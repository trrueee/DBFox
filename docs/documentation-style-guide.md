# DBFox 文档编写与维护规范

> 文档类型：维护规范
>
> 状态：当前
>
> 最后核验：2026-08-21
>
> 适用范围：根目录说明、`docs/`、发布说明和代码内文档链接

本规范用于保证 DBFox 文档容易查找、容易理解，并且与当前实现同步。它借鉴成熟技术文档常见的做法：按读者任务组织内容、使用单一事实来源、使用简洁直接的语言、把历史资料与当前合同分开。

## 1. 基本原则

1. **先写读者要解决的问题。** 开头说明适用对象、适用范围和读完后能完成什么。
2. **一处维护一个事实。** 同一协议、状态机或安全边界只在一份权威文档中定义，其他文档使用链接引用。
3. **区分事实、决定和计划。** 已实现行为写“当前”；已经批准但仍需长期维护的架构选择写“已接受”；尚未决定或未实现的内容写“草案”。
4. **使用通俗中文。** 能说“运行状态”就不说“运行态势感知”；能说“找到历史消息”就不说“记忆回灌”。代码中的正式名称保留英文，并在首次出现时解释。
5. **文档和实现一起变化。** 修改公开行为、系统边界、命令、配置或支持平台时，在同一批变更中更新文档。
6. **不把配置当作验证结果。** CI 配置、平台分支或打包脚本只能证明“具备构建合同”，不能证明真实产物已经安装和运行成功。

## 2. 文档分类

| 分类 | 目录或文件 | 回答的问题 | 示例 |
| --- | --- | --- | --- |
| 项目入口 | 根 `README.md` | 这是什么，能做什么，如何开始？ | 能力、架构概览、快速开始 |
| 架构说明 | `docs/architecture/` | 系统为何这样划分，状态由谁负责？ | 进程、数据流、不变量、ADR |
| 实现指南 | `docs/backend/` | 当前代码怎样工作，如何排查和修改？ | 调用链、失败路径、代码索引 |
| 规范参考 | `docs/specs/` | 用户可见行为和跨模块合同是什么？ | 状态、字段、验收场景 |
| 质量与发布 | `docs/quality/` | 如何测试、评测和发布？ | 门禁、评测方法、发布矩阵 |
| 历史资料 | `docs/archive/` | 过去为什么这样做，后来被什么取代？ | 旧设计、阶段报告、审查记录 |

不要因为内容较长就新建文件。只有当主题、读者或维护周期明显不同，且能指定唯一入口时，才拆分文档。

## 3. 文件和目录命名

- 文件名使用小写英文和连字符，例如 `system-overview.md`。
- `README.md` 只用于目录入口；内容页使用能说明主题的文件名。
- 不使用 `final`、`latest`、`new`、`v2`、`最终版` 等无法长期维护的名称。
- 日期只用于历史报告、事故记录和阶段计划，例如 `2026-08-12-release-review.md`。
- 图片统一放在 `docs/images/`；文件名说明内容，不使用截图工具生成的随机名称。
- 代码、配置、命令和正式协议字段保留原名；普通说明优先使用中文。

## 4. 当前文档的页眉

除根 `README.md` 外，当前文档使用以下页眉：

```markdown
# 清楚、可搜索的中文标题

> 文档类型：架构说明
>
> 状态：当前
>
> 最后核验：2026-08-12
>
> 适用范围：相关模块、版本或平台
```

允许的状态只有：

| 状态 | 含义 | 使用要求 |
| --- | --- | --- |
| 当前 | 描述当前实现、操作或验证合同 | 必须能指向源码、配置或测试 |
| 已接受 | 已批准并实施或正在实施的架构决定 | 说明决定、理由和重新评估条件 |
| 草案 | 尚未形成正式合同 | 不得写成已经支持或已经通过 |
| 历史 | 已被替代，仅供追溯 | 放入 `archive/` 并指向替代文档 |

“已完成”“已通过”不能作为永久状态。验证结论必须同时记录提交、平台、命令或产物。

## 5. 推荐内容结构

不同类型的文档不需要套用同一个模板，但应按读者阅读顺序组织。

### 5.1 架构说明

1. 目标和非目标；
2. 系统边界和所有权；
3. 主要流程；
4. 数据和状态；
5. 失败与恢复；
6. 安全和隐私；
7. 实现入口与验证证据；
8. 已知限制。

### 5.2 实现指南

1. 读者要完成的任务；
2. 前置条件；
3. 正常路径；
4. 常见失败和定位方法；
5. 修改边界；
6. 测试命令；
7. 相关架构合同。

### 5.3 规范参考

1. 适用范围；
2. 术语；
3. 输入、输出和状态；
4. 必须满足的规则；
5. 错误语义；
6. 验收场景；
7. 兼容性和版本边界。

### 5.4 质量与发布

1. 验证目标；
2. 环境和版本；
3. 命令或工作流；
4. 通过条件；
5. 不能证明的内容；
6. 证据保存位置。

## 6. 中文和术语

- 句子尽量短，一段只表达一个主要意思。
- 使用主动语态，明确责任主体，例如“Electron Main 生成令牌”，不要写“令牌会被生成”。
- 首次使用缩写时给出全称或中文解释。
- 不自行发明近义词。同一个概念在全部文档中使用同一个名称。
- `Agent Harness`、`Provider`、`Artifact` 等代码领域词可保留，但首次出现时应链接到[术语表](glossary.md)或就地解释。
- 避免把设计偏好写成事实，例如“更先进”“企业级”“完全安全”。使用可以验证的描述。
- 避免使用“显然”“简单地”“只需”等可能掩盖前置知识的词。

## 7. 链接、图表和代码

- 仓库内部使用相对链接；链接文字描述目标内容，不使用“点这里”。
- 关键架构图在 README 中使用仓库内静态 SVG，保证 GitHub、编辑器和离线阅读都能显示。
- 需要频繁维护的流程图可以在详细文档中使用 Mermaid；图旁必须有文字说明，不能让图成为唯一信息来源。
- 代码块标明语言；命令块应能从仓库根目录或明确说明的目录执行。
- 不复制大段生产源码。使用文件和 Symbol 链接，并解释其职责和边界。
- 表格适合对比和矩阵，不用于承载长段说明。

## 8. 文档更新检查表

提交前确认：

- [ ] 标题能说明页面主题，文件名符合命名规则；
- [ ] 页眉包含类型、状态、最后核验日期和适用范围；
- [ ] 当前事实与源码、配置和测试一致；
- [ ] 计划或未验证内容已明确标记；
- [ ] 没有创建第二份协议或状态定义；
- [ ] 新术语已解释或加入术语表；
- [ ] 相对链接和图片可以从当前文件打开；
- [ ] README、目录导航和相关代码索引已同步；
- [ ] 被替代内容已移入历史目录并指向当前文档；
- [ ] 修改架构、规格或发布承诺时，已增加对应验证。

## 9. 评审标准

文档评审依次检查四件事：

1. **准确：** 是否与当前实现和验证证据一致？
2. **完整：** 读者是否能理解边界、正常路径和失败路径？
3. **清楚：** 是否使用统一术语和通俗中文？
4. **可维护：** 是否只有一个事实来源，链接和索引是否稳定？

纯粹的措辞偏好不应阻塞提交；事实错误、状态不清、链接失效和重复合同必须修正。
