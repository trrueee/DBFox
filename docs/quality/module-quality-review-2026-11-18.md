## 结论先行

DBFox 已有真实的本地 Agent Harness 主干：一个耐久 Agent 循环、统一工具准入与审批、文件与进程能力、受限电脑操作，以及可检查的成果。Core 与 DLC 的边界总体成立，不宜推倒重写。当前质量短板集中在跨入口异步协作、长会话状态发现、审批信息完整性和少数长操作的事务边界。

本轮确认三项问题，另列一项高可信性能风险。没有发现可凭本轮证据定性为直接授权绕过或跨会话数据泄漏的问题；这不是完整安全审计结论。视觉设计已有统一令牌、原生字体和分层组件基础，但部分视图把运行状态、来源、限制和操作同时铺开，信息优先级仍需收敛。

设计目标是“当前任务 → 必要决策 → 可检查成果”。保留重要风险与停止入口；普通过程、技术字段、历史记录按需展开。具体方案及可操作的静态原型见 [交互收敛方案](../specs/workbench-interaction-refinement.md)。方案为草案，本轮未修改生产逻辑或重新发布安装包。

## 2. 核心路径与所有权

| 路径 | 控制与数据流 | 必须保留的边界 |
| --- | --- | --- |
| 开始工作 | Project / Workbench → 草稿或既有 Session → HTTP 准入 → SQLite → Coordinator / RunLoop | UI 负责输入和投影；耐久状态由后端持有 |
| 工具执行 | 原生 Responses function call → Registry → Policy / Admission / Approval → Invocation → Observation / Settlement | 只有一套工具执行与审批语义，无供应商名分支 |
| 修改与验证 | Workspace 绑定及 generation → 文件工具 → Local Execution Broker → OS Job / 日志 → Artifact | Run、Invocation、Job、Process 是不同身份；启动受理不等于成功 |
| 电脑任务 | 显式目标共享 → 对话 / generation / 权限 / 到期检查 → 观察 → 单次审批 → 输入 → 再观察 | 普通 Windows 桌面、显式共享窗口及独立 Edge；不是任意电脑权限或 OS 沙箱 |
| 数据任务 | Resource 授权 → SQL validate → 不可变校验 Artifact → readonly execute → Result / Representation | 不接受模型绕过校验直接执行原始 SQL；模型只取有界数据 |
| 成果工作台 | 同一 Artifact → Representation → 通用 / DLC 视图 → 导出或打开 | Dock 与 Zustand 是显示状态；不增加第二份业务事实 |
| 扩展与模型 | Host 管理包 / 信任 / 启用 / 重启；Provider 管理模型传输 | 本地模型是低成本验证与运行选项，不定义核心工具语义 |

Electron Main 的 EngineSupervisor 持有 Sidecar、短期令牌和 generation；SQLite / Alembic 持有本地事实；系统凭据库存放秘密；受托管进程由 Windows Job Object 管理。借用的原生应用窗口并非 DBFox 拥有的进程，不能把停止输入等同于撤销已发生的外部业务操作。

### 有证据的构造亮点

1. `engine/api/conversation_commands.py` 在耐久准入与附件入场提交后才通知调度，符合“先事实、后发布/唤醒”的方向。UI 重试复用准入幂等键，已有失败恢复测试。
2. `engine/agent/model_media.py` 与 RunLoop 读取公共 Representation，保留一张有界最新图片；图片过期明确告知，不向数据库上下文塞入 base64，也不为视觉模型另建执行链。
3. `dlcs/dbfox_data/backend/sql/sql_admission.py` 绑定校验工件、SQL、资源、执行来源和审批主体；`sql_backed_view.py` 复用 SQLGlot，不自行拼出一套 SQL 文法解析器。
4. `desktop/src/features/dock/ExecutionLogView.tsx` 将状态、实际退出码、输出是否完整分别显示，并保留失败时的旧输出和错误。比把“请求成功”画成“任务完成”更可靠。
5. UI 已用语义令牌、Phosphor 图标、Radix 与系统字体。其统一基础应继续使用，质感主要从层级与比例获得，不需要再引入皮肤框架、远程字体或全页面玻璃特效。

### Q1：草稿会话创建没有跨入口合并

- **位置：** [ConversationCenter.tsx:66](../../desktop/src/features/appShell/ConversationCenter.tsx#L66)，另见发送路径第 87–89 行和 [ComposerContext.tsx:31](../../desktop/src/features/conversation/workspace/ComposerContext.tsx#L31)。
- **结论状态 / 类型：** 已确认缺陷；异步一致性；中等严重，高优先级。
- **证据与复现：** 挂载真实 ConversationCenter，只替换创建请求、文件选择边界和外部 Dock 打开。电脑入口与附件的 ensure 回调在第一次创建完成前同时调用，实际创建函数调用两次；让附件请求先返回 `attachment-session`，电脑请求后返回 `computer-session`，最终 draftConversationId 被后者覆盖。两个入口分别得到不同 Session。
- **触发条件与根因：** 先检查已存在 ID，再 await 创建，没有记录创建中的操作。电脑入口的 openingComputer 只在子组件本地；父组件的附件和发送路径看不到该状态。发送路径也能自行创建 Session。
- **影响范围：** 多余会话、上下文突然切换、附件和电脑目标属于不同草稿，随后发送可能被后端的附件所属校验拒绝。后端所有权校验仍在，不能据此声称跨会话数据泄漏。
- **建议修复：** 在现有草稿所有者处，按稳定 scope 保存唯一创建中操作，创建成功再存唯一 Session ID；发送、附件、电脑都复用。scope 改变时旧结果只归原 scope，不写当前 scope；失败清理创建中的记录以允许显式重试。仅禁用按钮不能覆盖多入口与同一事件循环的竞态。不要引入新的 Session 模型或全局任务调度层。
- **建议回归：** 三入口同时请求只创建一次；乱序完成、创建失败后重试、项目切换、草稿提升、组件卸载均不污染当前工作区；附件和共享引用必须归同一 Session。

### Q2：历史条数上限遮蔽有效电脑共享

- **位置：** [store.py:50](../../engine/computer/store.py#L50)、[store.py:157](../../engine/computer/store.py#L157)、[ComputerDock.tsx:51](../../desktop/src/features/computer/ComputerDock.tsx#L51)。
- **结论状态 / 类型：** 已确认缺陷；资源发现与操作可见性；中等严重，高优先级。
- **证据与复现：** 用实际 SQLAlchemy 模型、实际 ComputerGrantStore 和内存 SQLite，创建一个 30 分钟窗口授权，再创建/替换 17 个浏览器授权。旧窗口 require 仍返回 active，但 list 的 16 项中没有该窗口，descriptors 也不包含它。无 OS 窗口或进程被创建。
- **触发条件与根因：** `_list` 先按创建时间倒序 limit(16)，`descriptors` 在此后才筛选 ACTIVE。UI 又对列表 slice(0, 8)，进一步让有效项可能在历史后被省略。
- **影响范围：** 长会话里仍有效的目标无法从面板或新一轮资源发现找到，用户难以辨认与逐个结束共享。已有目标引用仍受 require 权限/代次检查；不是授权绕过，也不表示全局停止入口失效。
- **建议修复：** 使用同一个 Store 的权威条件单独查询有效共享（或先按有效状态排序且保证不受历史分页截断），历史记录单独分页。API 和 UI 必须保证所有有效项可见；不要在 UI 复制一份授权缓存补漏。
- **建议回归：** 超过 16 条历史、两个种类同时有效、到期与暂停、engine generation 变化、其他会话隔离；检查资源发现、活动状态和逐目标停止。

### Q3：坐标操作的审批没有显示位置

- **位置：** [tools.py:151](../../engine/computer/tools.py#L151)、[ComputerApprovalDetails.tsx:9](../../desktop/src/features/computer/ComputerApprovalDetails.tsx#L9)、[ApprovalCard.tsx:209](../../desktop/src/features/conversation/workspace/ApprovalCard.tsx#L209)。
- **结论状态 / 类型：** 已确认展示缺陷；审批可理解性；中等严重，高优先级。
- **证据与复现：** 后端 approval_review 已提供 position。前端只选 target/action/element/url/text/key/time；坐标点击 element 为“画面位置”。DOM 测试将落点从 (0.2, 0.25) 改为 (0.85, 0.75)，可见审批全文不变。ApprovalCard 对 computer 提前返回此组件，不显示普通参数详情。
- **触发条件与根因：** 无 UIA / DOM 节点的画布等任务使用相对坐标；专用审批视图丢弃了位置字段。模型和后端有区别，用户看到的决策信息没有区别。
- **影响范围：** 用户无法核对点击目标。后端仍将批准绑定到精确 input 和资源；不能把这描述为任意动作复用审批。
- **建议修复：** 坐标操作至少显示相对位置、坐标基准及观察时间；可用时展示该次真实观察缩略图和落点标记。所需观察/Artifact 关联若要跨 API，修改权威合同并重新生成客户端，避免通过查询“最近截图”猜对应关系。证据不可用或过期时明确要求重新观察。文本输入、网址与敏感接管说明保持可见。
- **建议回归：** 不同点可区分；节点 / 坐标 / 导航审批分别可理解；图片过期、窄面板、键盘与读屏；批准仍只对应原动作，不能批准后自动重放。

### R1：导航等待在 SQLite 写围栏内执行

- **位置：** [runtime.py:210](../../engine/computer/runtime.py#L210)、[store.py:114](../../engine/computer/store.py#L114)、[browser.py:284](../../engine/computer/browser.py#L284)。
- **结论状态 / 类型：** 高可信性能风险；并发与事务延迟；中等严重，中优先级。本轮未跑慢网端到端量测，不声称已发生 UI 卡死或心跳丢失。
- **证据与触发条件：** effect_lease 开启写事务，yield 内调用 perform；浏览器 navigate 的 perform 调用 `page.goto(wait_until="commit", timeout=4000)`。等待首个提交可能长达约 4 秒，包含网页网络等待。SQLite 同一时刻只有一个写事务，其他写入会竞争该锁。[SQLite 官方事务说明](https://www.sqlite.org/lang_transaction.html)
- **根因与影响：** 安全围栏预期只包即时输入分派，实际包含同步浏览器等待。慢站点可能增加共享停止状态持久化、Run 事件与其他本地写入的延迟；最终是否超时依赖具体 busy_timeout 和并发负载。
- **建议修复：** 先用可控延迟站点测事务持有时间和停止延迟。调查 Playwright 官方导航边界后，采用能把输入分派与后续观察等待分开的最小改变；如当前同步 API 不能满足，应明确记录延迟上限和可接受性，不能简单把权限复查移出围栏。保持 Event 在数据库竞争前设置、杀所属浏览器 Job 的顺序，以及结果未知后不重放的语义。
- **建议回归：** 慢导航时另一会话准入与事件写入、同时停止、浏览器中途退出、URL 拒绝、超时后的重新观察；断言无第二次导航或点击。

## 5. 成熟方案复用与层次评估

| 区域 | 已调查 / 可用方案 | 决策、成本与退出方式 |
| --- | --- | --- |
| 草稿并发 | 现有 Workspace scope / Conversation Store；已依赖 TanStack Query 的 mutation scope | 复用现有 owner，做局部请求合并即可。Query mutation scope 可串行，但串行两个“创建”仍可能产生两份记录，不能当作自动去重；不新增缓存库或状态机。无新增供应链与许可证风险。[官方说明](https://tanstack.com/query/latest/docs/framework/react/guides/mutations) |
| 后端任务运行 | Coordinator、RunLoop、持久仓库；Python 并发标准库 | 保留现有小型调度。当前本机资源所有权与耐久状态要求，不适合仅为代码整齐换成外部队列。以后确有跨机调度需求再调查迁移；本轮无引入理由 |
| SQL 与表格 | 已有 SQLGlot、TanStack Table / Virtual、公共 DataFrame Representation | 直接复用；不新建 SQL parser、表格数据副本或单 DLC 私有结果 API。相关依赖的所有版本漏洞与许可证并未在本轮全面扫描，不把“成熟”当安全证明 |
| 桌面 / 浏览器驱动 | Win32 / UIA、Windows Job Object、Playwright 官方能力 | 这些适配处于真实 OS 边界，合理保留。需严格控制 COM/PW 的 Any 和平台线程约束向内部扩散；不因只有一个 Windows 实现而预造更多跨平台接口 |
| API / 表示转换 | Pydantic → OpenAPI 生成客户端；Artifact → Representation → renderer | 都位于真实边界，保留一次单向转换。禁止手改生成客户端、把 DLC payload 镜像成第二份 Host DTO、或者同时维护旧新字段映射 |
| UI 基础 | 已有语义 tokens、Radix、系统字体、Phosphor；Apple HIG 的层级与渐进披露 | 继续复用现有体系，只改组合和密度。UI 技能推荐的营销型布局、青橙配色和远程字体不适合当前桌面工作区，未采用；不新增商业字体或品牌资产授权负担 |

本轮未建议新增兼容层、双写或私有 fork。若未来为旧安装包做迁移，必须记录真实版本约束、所有者和删除条件；不能以“临时”命名永久承载核心规则。

表格 hook 在 source 改变时保留旧行最初是调查假设。继续追踪发现 ArtifactViewHost 在新 artifact 的表示发现期间会卸载旧表示视图，Dock 按 viewKey 也有重挂载边界。因此本轮没有证明它会在正常切换成果时错贴数据，未列为确认缺陷。未来直接复用 hook 时需明确 source 身份契约；React 的状态身份规则支持此类验证。[React 官方说明](https://react.dev/learn/preserving-and-resetting-state)

## 7. 克制的修复与设计落地顺序

1. 为 Q1 / Q2 / Q3 加入正式回归，然后修源头。一个问题一个小改动，不混入外观重写。保留本轮复现证据作为修复前对照。
2. 将唯一草稿请求、有效共享查询和完整审批合同稳定下来。用现有 API 生成与类型检查约束前后端，不加 mapper 或镜像状态。
3. 量测 R1。只有能保持停止围栏与精确动作授权时才缩短事务；不可用“异步化”取消安全顺序。
4. 按场景逐个收敛 UI：任务上下文行、过程折叠、交付行、来源检查器、电脑共享摘要。沿用现有 tokens 和组件；每次修改附深浅色 / 窄宽 / 键盘检查。
5. 合并过时的系统概览定位与当前实现地图。设计草案只有真正实现并验证后才标记为当前。

不建议按“超过多少行”拆 Coordinator、ComputerRuntime 或 DlcCenter。应观察真实变更原因：UI 状态、包管理动作、审批决策、OS 输入和事务生命周期是否需要独立修改。长度只帮助定位，不能证明架构错误。

每一步都可以单独撤回；不引入双系统切换或兼容数据迁移。未来实现负责人以对应模块维护者为准，本轮不虚构人员分配与完成日期。

## 8. 验证限制

没有重新调用付费 API、重跑本地模型矩阵、访问用户业务应用或数据库、安装安装包、运行远程 CI、验证 macOS/Linux 电脑能力。本轮没有依赖漏洞全量扫描、渗透测试、可用性用户实验或像素级跨设备全覆盖，因此不提供虚假的百分制质量评分，也不承诺“任何工作都能做”。

可确认的是：主干能力与工程约束有实质基础；本轮三个缺陷可以清楚定位并局部修复。下一步应优先减少异步与授权可见性的不确定，再将界面密度收敛到当前任务本身。
