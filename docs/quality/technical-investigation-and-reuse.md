# 技术调研、方案复用与架构克制

> 文档类型：质量参考
>
> 状态：当前
>
> 最后核验：2026-08-16
>
> 适用范围：所有技术方案的选型与实现，包括前端 UI 组件、交互实现与资源素材选择
>
> 权威配置：无（本文件为过程性约束，由评审、[PR 模板](../../.github/pull_request_template.md) 与架构文档共同执行）

在实现任何非简单功能、基础设施能力或技术方案之前，必须先进行与问题规模相匹配的调查，不得在不了解现有方案的情况下直接自行实现。

## 1. 实现前先调查

开始编码前，依次检查：

1. 当前项目中是否已经存在相同或相近的能力。
2. 当前依赖、语言标准库、框架或平台是否已经提供官方实现。
3. 官方文档、主流社区、成熟开源项目或参考实现中是否已有经过验证的方案。
4. 项目历史代码、ADR、issue、提交记录中是否已经讨论或否决过类似方案。

对于重试、缓存、序列化、协议解析、鉴权、权限控制、任务调度、状态机、并发控制、数据库迁移、日志、配置、事件总线、网络通信、文件处理等通用能力，尤其不得未经调查就自行设计。前端对应物包括：组件库与交互原语、图标与素材、状态管理与持久化、虚拟列表、SQL/代码编辑与高亮、拖拽、快捷键与命令面板、表单与校验、动效实现等。

调查深度应与功能的风险、复杂度和长期维护成本相匹配。简单的局部逻辑不需要过度调研，但高风险或通用基础能力必须有充分依据。

“非简单功能”的建议判据（满足任一即先调查）：涉及持久化、跨进程、网络、协议、安全、鉴权、数据模型、迁移或审计；预计跨越多个提交或多个模块；失败或返工成本高；存在成熟通用方案却仍倾向手写。

## 2. 明确作出复用或自研决策

调查后，应明确选择以下一种方案：

- 直接复用项目内已有实现；
- 使用标准库、官方组件或成熟第三方方案；
- 在成熟方案上进行最小封装或适配；
- 因明确约束而自行实现。

不得仅因为“可以自己写”就选择自研，也不得仅因为某个第三方库流行就盲目引入依赖。

选择方案时至少评估：

- 是否真正符合当前需求；
- API 和数据模型是否匹配；
- 项目成熟度与维护状态；
- 安全性和历史漏洞；
- 性能与运行成本；
- 许可证和合规风险；
- 依赖体积与供应链风险；
- 集成、升级、迁移和退出成本；
- 是否会引入供应商锁定；
- 团队是否具备长期维护能力。

当决定自行实现时，应说明为什么现有方案不适用，而不是默认跳过调查。

## 3. 禁止重复造轮子

发现成熟、稳定、适配度高的现有实现时，应优先复用，不得创建功能重复但质量、测试和维护能力更弱的自定义版本。

如果现有方案只缺少少量功能，应优先：

1. 使用其扩展机制；
2. 编写小型适配器；
3. 向上游贡献；
4. 在清晰边界内补充缺失部分。

不要复制整个方案并长期维护一个私有分叉，除非有明确且经过记录的必要性。

“小型适配器”与“堆叠中间层”的边界：适配器只允许位于真实系统边界，做一次单向类型/协议翻译，不复制业务规则、不保存第二份状态，并能回答第 4 节的八个问题。任何双向映射、可写状态或规则复制都不属于小型适配器。

## 4. 避免通过堆叠中间层解决根本问题

修复问题时，不要默认增加新的兼容层、映射层、转换层、包装器、门面、代理、DTO、镜像数据模型、字段重命名表、双向同步逻辑、fallback 链或特殊分支。

在增加中间层之前，必须先回答：

1. 真正的问题是否可以在源头修复？
2. 是否可以统一数据模型或接口契约？
3. 这一层是否位于真实的系统边界？
4. 它是否只是为了掩盖上下游设计不一致？
5. 它是否复制了已有业务规则？
6. 它是否会产生第二份事实来源？
7. 它是否会导致多次转换、双向映射或状态不同步？
8. 将来由谁删除，满足什么条件后删除？

应优先选择：修复根因；建立唯一的规范数据模型；统一接口和字段语义；在真实边界上进行一次单向转换；删除无价值的透传层；让调用方直接使用稳定契约；用类型、测试和契约约束替代运行时映射。

## 5. 临时兼容层必须可退出

只有在无法立即修改外部系统、需要渐进迁移、必须保持旧版本兼容或存在明确发布约束时，才允许增加临时兼容层（前端对应的典型形态：预览样板页、mock 数据层、待接入的占位组件）。

临时兼容层必须具备：

- 明确适用范围；
- 明确负责人；
- 明确删除条件；
- 与风险相称的可观察退出证据（使用量、日志、编译期引用检查或等价指标）；
- 按风险分级的独立测试；低风险短命 facade 可只用编译期反向引用测试证明删除条件；
- 不承载新的核心业务逻辑；
- 不继续被其他模块依赖；
- 后续移除计划。

没有退出条件的“临时层”应视为永久技术债务。

## 6. 保持架构层次最小化

每增加一个抽象、接口或中间层，都必须能够说明它解决了什么真实变化轴或系统边界。不要为了“以后可能会用到”、形式上的解耦或模式完整性提前创建抽象。

以下情况通常属于不良设计信号：

- 多个结构相同但名称不同的数据模型；
- 对象在多个层之间反复转换；
- 只有一个实现且不存在真实替换需求的接口；
- 仅转发参数和返回值的包装层；
- 为兼容内部错误设计而长期保留的适配器；
- 同一业务规则在多个 mapper、service 或 controller 中重复；
- 新问题通过继续增加一层来解决；
- 新旧协议无限期并存；
- 双向映射和双写逻辑缺少一致性保障。

优先采用最简单、直接、可测试、可删除并且符合当前真实需求的设计。

## 7. 输出决策依据

对于重要技术决策，在回复或实现说明（PR 描述、组件注释、设计文档）中简要列出：

- 调查过的现有方案；
- 最终采用的方案；
- 未采用其他方案的原因；
- 新增依赖或自研实现的主要风险；
- 是否新增兼容层、映射层或迁移债务；
- 后续验证与清理方式；
- 决策记录位置：PR 描述、组件注释、设计文档或 ADR；影响数据模型、wire、安全、迁移或跨模块合同的决策必须落入 `docs/architecture/` 或 `docs/specs/` 中标记为“当前”的文档或 ADR。

如果当前环境无法访问互联网、官方文档或依赖信息，应明确说明调查限制，不得据此声称“没有成熟方案”。
