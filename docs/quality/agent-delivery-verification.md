# Agent 交付可靠性复审

> 文档类型：质量复审
>
> 状态：当前
>
> 最后核验：2026-11-26
>
> 适用范围：Windows x64 工作树，Git 基线 `1aa7e770a305`

DBFox 的 Run 终态记录任务交付结果。引用校验确认来源可访问且本次运行成功观察过该来源。
可计算的业务结论还需要独立核对指标口径和结果。验收分别看用户要求是否完整送达、操作是否真实结算、
答案是否满足交付要求，以及已声明的业务条件是否得到验证。

## 本轮复现与修复

| 复现 | 根因 | 当前行为 |
| --- | --- | --- |
| 长请求在较小预算下仍发往模型 | Prompt Planner 允许裁掉必需消息尾部 | 原请求完整进入模型，预算不足走既有明确失败路径 |
| 28 条已生效补充指令只出现 24 条 | 补充指令和最近历史共用一个查询上限 | 从持久 Input 按准入顺序读取，超出预算明确停止 |
| 先前被拒绝的答案在工具结束后成为部分成果 | RunLoop 缓存早先候选，恢复查询也跨 Turn 寻找候选 | 交付和恢复使用当前 Turn，工件继续按已结算事实保留 |
| 最后一轮提交有效引用被标记为部分完成 | 完成策略用轮次序号推断交付状态 | 能通过完整校验的最后一轮正常完成，硬停由受限交付路径处理 |
| 故事核验接受另一个资源的同号代次 | 领域约束只比较代次数字 | 用工具执行的 ResourceScopeRef 和实际观察代次匹配，检查每个世界的写入时序 |
| 跨表对账得到可引用的错数 | 订单和明细连接后，同一订单金额按明细行重复累加 | Data 从已解析的 SQL 给出跨源聚合粒度提示，原只读校验继续独立判定 |
| 缺少试次结果的 Bench 可返回成功 | CLI 仅比较成功数与已评分数，两个空集合也相等 | 每个试次必须通过，基准查询独立于 Agent 是否产出 SQL |

运行时沿用 ContextBudgetPlanner、耐久 Turn、CompletionPolicy、ResourceScopeRef 和现有结算事务。
协议、数据库和 DLC SDK 保持兼容。SQL 粒度提示使用已有 SQLGlot AST，只分析可识别的作用域，
对比多个来源的 `SUM`、`AVG` 或 `COUNT` 时提醒核对连接粒度或分别聚合。[Looker 对连接后重复聚合的说明](https://docs.cloud.google.com/looker/docs/best-practices/understanding-symmetric-aggregates)

## 十三项结论与验收边界

| 编号 | 当前源码与设计 | 验收边界 |
| --- | --- | --- |
| P0-1 Provider | 两种协议共用选择、设置和装配，Provider 负责原生工具与续轮翻译 | Chat 和 Responses 合同由 Core 测试覆盖，真实模型本轮使用本机 Ollama，云端端点待验收 |
| P0-2 上下文 | 保留完整当前输入和最近完整工具轮次，按预算淘汰旧轮次，通过证据索引召回 | 保留模型窗口估算误差。后续压缩评审依据长会话证据召回率、请求体和实际 Token 数据 |
| P0-3 恢复预算 | Provider 重试与进程中断恢复由独立计数控制 | 保留恢复超限、原生记录及未知副作用不重放的 Core 合同 |
| P0-4 审批与令牌 | 执行前核对审批期限、操作及资源版本。Sidecar 对令牌按字节恒定时间比较，非法编码走同一 401 | 当前是同一本机工作台主体。会话凭证需要由独立的 Host 授权入口签发，在所有读写、事件及成果路由消费相同作用域 |
| P1-5 Session Memory | 从现有持久字段投影有界的工作集和证据引用 | 继续以工件可用性与版本校验证据，历史上下文恢复使用原文查找 |
| P1-6 完成判定 | 使用全部已结算观察和当前候选，区分成功交付、强制部分结果和失败 | 通过真实 RunLoop 重现旧候选错发与末轮错标并验收，业务内容另按领域条件核查 |
| P1-7 工件事务 | Artifact、Invocation、Observation 由 ToolSettlement 同一事务结算 | 故障注入核验数据库回滚。外部进程或远端写入的未知状态继续按恢复合同结算 |
| P1-8 SQL | Data 负责 Catalog、只读执行、时限、取消与粒度提示，模型观察带执行范围 | MySQL 本机集成通过。MariaDB 和 PostgreSQL 的真实服务待验收 |
| P1-9 冻结工具 | Ollama 的 Schema 来自同一 Turn 的冻结物化，Invocation 复核工具身份与授权 | Core 物化合同和本地 Qwen 生产调用链均覆盖 |
| P2-10 复杂度 | 删除旧候选缓存和静默截断分支，按现有所有者拆分历史和活动输入读取 | Dispatcher 与 Context 的后续整理按可验证职责安排，每次先保留调用语义 |
| P2-11 死代码 | 删除仅写入的 `policy_fingerprint`，继续在审批执行边界比较实际授权参数与当前合同 | 保留真实审批、工具恢复和运行超限回归 |
| P2-12 门禁 | 严格 marker 与确定性 Core 套件继续入闸，完整试次通过才返回成功，独立保留业务预期结果 | 跨版本比较需要固定样本和对照基线，覆盖率阈值待工程基线支持 |
| P2-13 DLC | Core 提供已冻结的调用范围和完成约束扩展点，Story 在原约束内校验精确版本 | 领域版本仍由各模块持有。提取共享原语应以两个以上相同失败和恢复语义为依据 |

当前凭证的签发者与持有者是同一个本地应用。未来需要给脚本或扩展授予会话级访问时，先把签发资格
留在校验发送方的 Electron Main 或等效受信入口，再对会话和操作范围做统一检查。授权回归应覆盖
跨会话读取、审批、取消、事件订阅、旧凭证撤销与运行代次切换。[Electron IPC 发送方校验](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages) · [Bearer 凭证的持有者语义](https://www.rfc-editor.org/rfc/rfc6750#section-1.2)

MCP 接入复用 Tool 注册、Policy 和 Invocation；子代理的产出需经父任务可检查的证据链；Skills
在上下文中有独立来源；无界面客户端复用输入、事件和成果 API。每项能力的验收应包含已确认的用户目标、
完成条件、真实结果和干预路径。业务验收优先在已有 CompletionConstraint 中用确定性程序检查用户明确要求的条件。

## 已保留的真实模型结果

使用已配置的 `qwen3.5:4b-q4_K_M` 与生产 RunLoop，原有计数及空值用例各通过两次。连接分组通过一次，
另一次得到正确结果但超过用例的轮数和工具调用预算。跨表对账两次失败。一次在 SQL 校验后收到
`MODEL_PROVIDER_INCOMPLETE`，没有执行查询。另一次将 137562.5 的订单总额算成 172102.5，
实际 SQL 在连接明细后才累加订单金额。原结果与代码修订后的复验分别保存于
`.tmp/deep-design-local-model/result/` 和 `.tmp/deep-design-grain-model/result/`。

复验中，连接分组通过 2/3，跨表对账通过 0/3。对账两次重复累计，一次得到正确的 2500 差额后
因答案交付校验未通过停止。基准值在缺少已执行查询时仍记录，便于隔离执行失败和业务值不一致。
粒度提示已经进入工具反馈，跨表核验仍需要独立的计算条件。

可核验的业务交付可以沿现有扩展点推进。调用方先确认条件与数据范围，Data 以各自的源表粒度
计算可复核的总额，使用相同来源版本核对报告值。代码任务可以用已约定测试的实际退出码及运行时
绑定的文件版本验证。Core 只消费当前 Run 的有效证据和约束结果，任意正文的语义需要对应的验收条件。
